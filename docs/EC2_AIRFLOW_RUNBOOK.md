# EC2 Airflow to S3 runbook

This milestone runs a small, single-host Airflow deployment on EC2. It is suitable
for the case-study implementation and development validation; it is not a highly
available production Airflow architecture.

## Data flow

1. The scheduled DAG generates deterministic synthetic healthcare staffing data.
2. Six tasks upload these independent source families in parallel:
   `operational`, `external`, `data_science`, `appcast`, `app_stream`, and
   `spreadsheets`.
3. Every uploaded object is checked against the locally generated byte count.
4. A final manifest is written only after all six source tasks succeed.
5. Objects land under `s3://BUCKET/raw/source=.../entity=.../load_date=YYYY-MM-DD/`.

## Prerequisites

- Complete `docs/AWS_ACCESS_SETUP.md` and verify `aws sts get-caller-identity
  --profile carematch-dev`.
- Apply `infra/terraform/s3` and copy its `bucket_name` output.
- Install Terraform, AWS CLI, and the Session Manager plugin locally.

Do not place access keys, Snowflake passwords, or tokens in `.tfvars`, `.env`, Git,
or chat. Terraform uses the local `carematch-dev` profile; EC2 uses its attached IAM
instance profile and therefore has no static AWS key.

## Deploy

```powershell
.\scripts\deploy_airflow.ps1 -BucketName "YOUR_BUCKET" -Action plan
.\scripts\deploy_airflow.ps1 -BucketName "YOUR_BUCKET" -Action apply
```

Cloud-init installs Docker, clones the repository, builds the pinned Airflow image,
initializes PostgreSQL, creates a random admin password, stores it as an SSM
SecureString, and starts the Airflow services.

## Open Airflow without SSH

```powershell
terraform -chdir=infra/terraform/ec2-airflow output -raw password_command
terraform -chdir=infra/terraform/ec2-airflow output -raw airflow_tunnel_command
```

Run the displayed password command, then start the displayed tunnel command. Browse
to `http://localhost:8080`, sign in as `admin`, enable
`carematch_synthetic_sources_to_s3`, and trigger it.

Port `8080` is bound only on the EC2 host and is not exposed by the security group.
Keep the SSM port-forwarding command running for the entire browser session. If the
browser reports that localhost refused the connection, verify the local plugin and
restart the tunnel:

```powershell
session-manager-plugin --version
aws ssm start-session --profile carematch-dev --region us-east-1 `
  --target INSTANCE_ID `
  --document-name AWS-StartPortForwardingSession `
  --parameters "portNumber=8080,localPortNumber=8080"
```

A successful tunnel prints `Port 8080 opened` and `Waiting for connections`. Verify
it independently with:

```powershell
(Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8080/health).StatusCode
```

The expected response is `200`. Do not add a public inbound rule for port `8080`.

## Verify S3

```powershell
aws s3 ls "s3://YOUR_BUCKET/raw/" --recursive --profile carematch-dev
aws s3 ls "s3://YOUR_BUCKET/manifests/" --recursive --profile carematch-dev
```
